# 5. Архитектурные решения

Все четыре ADR приняты для учебной версии проекта.

## ADR-001. Три сервиса с отдельными данными

**Контекст.** Нужно управлять заказом, местами двух перевозчиков и оплатой. Их правила различаются, а внешние базы нам не принадлежат.

**Варианты.** Один локальный сервис; сервис на каждый маленький шаг; три сервиса по ответственности.

**Решение.** Booking отвечает за заказ, Reservations — за брони, Payments — за деньги. Каждый работает только со своей БД. У двух перевозчиков разные внешние системы, но один наш сервис Reservations.

**Последствия.** Ответственность понятна, части можно менять независимо. Появляется обмен сообщениями. Три внутренних сервиса — выбранное разделение; невозможность общей транзакции объясняется внешними системами, а не количеством наших приложений.

## ADR-002. Последовательная saga

**Контекст.** После бронирования поезда паром может оказаться занят. SQL rollback не отменит уже сделанную внешнюю бронь.

**Варианты.** Общая распределённая транзакция; самостоятельная реакция всех сервисов на события; явный координатор шагов.

**Решение.** Booking последовательно запускает бронь поезда, бронь парома и оплату. При сбое отправляет отмены и при необходимости возврат. Это saga с компенсациями. Данные о текущем шаге сохраняются в БД.

**Последствия.** Процесс легко показать на диаграмме и восстановить после перезапуска. Компенсации требуют времени и сами могут временно не работать. Учебные перевозчики должны поддерживать полную отмену брони при срыве покупки; клиент получает билеты только после оплаты.

## ADR-003. RabbitMQ и outbox/inbox

**Контекст.** Сервис может сохранить заказ и упасть до отправки сообщения. Или обработать сообщение и упасть до подтверждения брокеру.

**Варианты.** Только HTTP-цепочка; брокер без дополнительных записей; брокер с outbox/inbox.

**Решение.** Использовать RabbitMQ. В outbox сохранять сообщение вместе с изменением данных. В inbox запоминать обработанные messageId. Подтверждать сообщение после commit. Для учебной версии достаточно одного брокера.

**Последствия.** Перезапуск процесса не теряет принятую команду. Дубликаты сообщений возможны, но не должны повторять бизнес-действие. В каждой БД нужны две небольшие служебные таблицы и фоновая отправка outbox.

## ADR-004. Постоянный ID операции и проверка неизвестного результата

**Контекст.** Платёж может выполниться, даже если ответ потерялся. Повтор с новым ID способен списать деньги второй раз.

**Варианты.** Считать тайм-аут отказом; повторять с новым ID; повторять и сверять по прежнему ID.

**Решение.** Последний вариант. Сначала записать PENDING-операцию, затем вызвать партнёра. При отсутствии ответа узнать результат по ID. Симуляторы хранят ID и результат весь срок заказа. Отмена или возврат считается завершённым только после подтверждения.

**Последствия.** Нет повторных списаний из-за сетевого сбоя. Для этого требуется поддержка идемпотентности у внешней системы. Пока она недоступна, нельзя честно объявить окончательный успех или отмену; заказ остаётся промежуточным.
