# 3. Контракты

- [openapi.yaml](openapi.yaml) — создать заказ и прочитать его состояние.
- [partners.openapi.yaml](partners.openapi.yaml) — HTTP API учебных перевозчиков и платёжного провайдера.
- [asyncapi.yaml](asyncapi.yaml) — четыре команды и шесть событий между сервисами.

Адреса localhost обозначают будущий стенд. Во второй части их можно изменить. Сейчас это только спецификации, работающих API ещё нет.

## Публичный API

`POST /bookings` принимает `routeId` и обязательный заголовок `Idempotency-Key`. Booking берёт два сегмента и цену из заранее заполненного каталога. Ответ `202` с bookingId и Location означает, что заказ сохранён. Затем клиент читает `GET /bookings/{bookingId}`.

Один ключ с одинаковым телом возвращает тот же исходный ответ. Тот же ключ с другим routeId даёт `409`. Уникальный ключ, заказ и начальное сообщение сохраняются одной транзакцией. Ключи не удаляются в течение учебной демонстрации. Новый ключ означает новую покупку.

Состояния заказа: `PROCESSING` — оформление, `COMPLETED` — обе брони оплачены, `CANCELLING` — отмена ещё идёт, `CANCELLED` — активных броней нет, деньги не списаны или полностью возвращены. Номера билетов возвращаются только для COMPLETED.

## Команды и события

| Команда | Кто исполняет | События результата |
|---|---|---|
| `ReserveLeg` | Reservations | `LegReserved` или `LegReservationFailed` |
| `CancelLeg` | Reservations | `LegCancelled` |
| `ChargePayment` | Payments | `PaymentCharged` или `PaymentFailed` |
| `RefundPayment` | Payments | `PaymentRefunded` |

AsyncAPI описывает точку зрения Booking: publish — отправить команду, subscribe — получить событие. Имена каналов совпадают с очередями в C4. Событие Failed означает установленный отказ, а не потерянный ответ.

Каждое сообщение содержит `messageId`, `bookingId`, `operationId`, `type` и `data`. `messageId` защищает от повторной доставки. `bookingId` связывает всё с заказом. `operationId` — постоянный ID конкретного действия, который также передаётся внешнему партнёру; событие возвращает ID вызвавшей его команды. Для поездки `legId=1`, для парома `legId=2`.

При создании заказа Booking заранее сохраняет один ID на каждый планируемый шаг `(bookingId, type, legId?)`. Повтор отправки не меняет ID и содержимое. Участник дополнительно запрещает второй платёж или вторую бронь сегмента того же заказа. Сумма приходит из снимка заказа и не изменяется при повторе. Несовпадающее содержимое с прежним ID — ошибка, а не новое действие.

## Тайм-аут и отмена

Перед HTTP-вызовом участник сохраняет операцию `PENDING`. При потере ответа он узнаёт статус по этому ID или повторяет запрос с тем же ID. Внешние симуляторы помнят результат весь срок заказа, поэтому повтор не создаёт новое списание или бронь. Возврат тоже имеет собственный постоянный ID.

`CancelLeg` отменяет ранее запущенную бронь. Даже если отмена пришла раньше резервирования, сервис сохраняет признак отмены и не запускает позднюю бронь. Для уже отправленного запроса сначала выясняет результат, затем отменяет созданную бронь. `LegCancelled` означает, что активной брони точно нет.

`RefundPayment` сначала запрещает новое списание, затем проверяет исход прежнего. Если деньги списаны — полностью возвращает; если списания не было — подтверждает нулевой результат. `PaymentRefunded` означает, что чистое списание равно нулю: `chargedMinor` и `refundedMinor` равны. Неизвестный исход оставляет операцию незавершённой.

Для простоты в каждом сервисе один обработчик, а изменение признака отмены и подготовка внешнего вызова выполняются под блокировкой строки заказа/сегмента. Уже подготовленный внешний запрос считается потенциально выполненным до сверки. Новые действия после начала отмены запрещены; поздний успех не возобновляет покупку.

У внешнего API `SUCCEEDED` и `FAILED` окончательны; `PENDING`, 5xx и потеря соединения требуют ожидания/сверки. `404` при поиске операции не доказывает отсутствие эффекта: повторяется исходный запрос с исходным ID. Это безопасно благодаря условию хранения ключей в симуляторах.
